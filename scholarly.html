1. Abstract

PoW - Pet Adoption on Web is a SPA-type web application, created to facilitate pet adoption process. The platform allows users to register, add pets and manage their resources, manage their adoption requests, all of this being available through a responsive interface. The application is built without any framework, using only HTML5, CSS3, JavaScript, PHP and SQLite for the database. The web application also allows media management, data export in CSV/JSON and RSS feeds, and also offers protection against XSS and SQL injection. This document describes the application interface design, architecture, data modeling and main features.

2. Introduction

This application was developed as part of a college project, with the aim of facilitating pet adoption through an easy-to-use platform. We used basic technologies (HTML, CSS, JavaScript, PHP, SQLite) and complied with all requirements. The application runs locally and does not use external services.

3. Interface Design and Justification

3.1 Design Choices

We chose a simple, clear and easy-to-read design to avoid visual overload and provide users with a friendly experience. The color palette used includes a main shade of green, symbolically associated with nature and animals, in contrast with a teal shade for highlighting. This contrast was chosen to visually differentiate the interface elements.

We opted for large visual components (e.g. buttons, cards, forms) and generous spaces between sections, to facilitate use on mobile devices. Each page of the application (e.g. add pets, requests, admin panel, etc) is accessible from a menu positioned at the top of the interface, but which is not persistent when scrolling. The footer was designed to remain consistent across pages and includes the application logo, the name of the currently logged-in user, and the application name.

In terms of fonts, only the login, registration and scholarly pages use the Verdana, Geneva, Tahoma, sans-serif font family to improve readability and provide a sense of clarity during user authentication. The rest of the application uses the browser's default font, usually Times New Roman, to maintain simplicity and focus on content rather than decoration.

As for the interfaces, we followed a consistent visual structure across all pages to ensure usability and predictability for the user. Each page follows the same layout logic (header with navigation, main section, and footer) to provide a uniform experience. Elements such as cards, buttons, and forms were designed to be intuitive, with clearly defined actions and enough spacing for touch-based interaction, especially on mobile devices.

We used display: flex with flex-direction: column for the overall layout of the page, to allow for vertically stack of main sections such as the header, main content, and footer. This structure is particularly beneficial for mobile responsiveness and greatly aids in reading content from top to bottom.

On the login page, we intentionally reserved space next to the login form for a registration area that can be accessed via a button, in order to improve usability and visual clarity.

3.2 Responsiveness and Usability

We made sure that the application interface is responsive, automatically adapting to various screen sizes, including mobile phones. This was achieved by using CSS techniques such as media queries.

Navigation between pages is done without reloading the entire site (SPA), thus contributing to a fluid experience. Animations were avoided, preferring simple loading of content.

On smaller screens, certain layout adjustments were made: menus are displayed vertically, font sizes are slightly increased for readability, and margins are reduced. Also here, we simplified the header by displaying only a menu button and a quick access button to the home page. When menu button is pressed, the other available pages are displayed. Without this approach, users would not have been able to access the basic functions of the application. The desktop version, on the other hand, displays the full horizontal navigation menu at the top of the screen.

To support a flexible and scalable layout across devices, we avoided absolute units like px in our CSS files. We opted for relative units like vw, vh, and percentages, which allow elements to resize automatically based on screen size.

4. System Architecture

4.1 Overview

We structured the application as a SPA (Single Page Application) web system, where: the frontend is written in HTML, CSS and JavaScript, and the backend is made in PHP with storage in SQLite. The frontend dynamically loads the content into the page using fetch(), without reloading the entire site. The backend responds to requests received from the frontend, performs operations on the database and sends the results in JSON format. PHP sessions were also used for authentication and access control.

4.3 Technologies Involved

For data export we used CSV/JSON format, also JSON was used for communication between JavaScript and the backend. In addition, the application also allows importing pets via CSV/JSON files, directly from the Add Pets page. The adoption feed is generated via RSS, with a limit of 10 pets displayed at most.

To ensure a smooth SPA experience, we used the fetch() method to implement asynchronous Ajax calls to the backend. These calls allow page content to be loaded without reloading the page. For example, forms send data using POST requests to PHP scripts that validate and send back a JSON. Also, pages like Add Pets, My Pets, and Requests use the fetch() function to retrieve or update pet data, send adoption requests, and receive notifications. The goal of this implementation is to reduce load time and facilitate a more pleasant user experience.

The application does not call external public web services, its own backend written in PHP works as a set of services, called asynchronously from JavaScript via fetch() and responding in JSON format.

The application contains template-related elements, dynamically loading reusable components, such as headers and footers, across all pages. Pet cards, buttons, and forms use a visual layout that ensures a consistent and scalable presentation style.

While the backend written in PHP is responsible for validating and processing the data, there is also minimal client-side validation using JavaScript to improve the user experience. For example, when uploading media files when adding a pet, the frontend checks if the files exceed the allowed size, avoiding unnecessary uploads. Also, some data entry fields use the required attribute in HTML to prevent empty submissions. These validations provide faster feedback to users. However, all critical validations (e.g. existence of an email in the database for registration), such as input data, are handled exclusively on the server side using PHP to ensure complete protection.

SQL Injection Protection: To protect the web application against SQL injection attacks, all SQL operations in the application are implemented using `prepared statements`. Thus, user data is treated separately from the SQL code, which prevents its direct concatenation in the query and reduces the risk of SQL injection attacks. Each user input is passed to SQL queries using the bindValue() method. This makes sure the data is safely processed and correctly added to the query using placeholders.

XSS Protection: To prevent XSS (Cross-Site Scripting), the application enforces strict validation rules for all user-entered data. Characters such as <, >, ", ' (which can be used to inject scripts) are not accepted in any input, as all form fields are validated against allowed formats (e.g., only letters, numbers, or certain specific characters). In the JavaScript code, the application uses .textContent instead of .innerHTML to insert user input into the DOM, ensuring that all content is treated as plain text, not executable code. On the server side, the PHP files do not use echo to output raw user input, and instead rely on input formats strictly validated before database insertion. For the RSS feed, all fields are previously validated and restricted, preventing any XSS from propagating into the feed. In addition, a Content-Security-Policy(CSP) meta tag was added to restrict script sources and prevent the execution of unauthorized code.

Access Control and Session Protection: The application implements a strict mechanism to protect resources. PHP scripts check if a user is authenticated using PHP sessions before performing any sensitive operations. Attempts to perform operations without being authenticated with the respective role redirect users to other content, ultimately not allowing the operations. Also, operations such as editing or deleting a pet are restricted by owner: only the user who owns the pet (based on their session ID) can access and modify its data. Even if the user tries to manually access the edit URL of another pet, the backend check denies access, thus preventing unauthorized changes. Similarly, access to the admin panel is strictly restricted to authenticated users with the administrative role.

4.4 Milestones

The project was developed in pieces, starting with certain important stages:

Project initialization - configuring the XAMPP environment, defining the directory structure and the SQLite database (e.g. several tables were added along the way, and some modified, initially we started with the table that has user management).

Authentication and sessions - implementing login/register functionalities and maintaining user sessions.

Pet management - developing pages for adding, editing and deleting pets, including media, then navigating adoptions.

Adoption requests and notifications - creating a mechanism for requesting and sending notifications.

Additional functionalities - CSV/JSON export, CSV/JSON import, RSS feed, HTML/CSS validation and XSS/SQL injection protection by checking all user inputs.

Architectural diagram & documentation - creating documentation related to the project.

5. Data Structure and Sources

5.1 Database Schema

The database consists of 7 tables and covers the functionality of the application. The tables include users, animals, media, requests, notifications, feeding_calendar and medical_history. Also, some tables are linked by relevant foreign keys (e.g. an animal is associated with a user by owner_id).

All data in the tables is provided by users through the application, where insertion is done through forms. Media resources (images, audio, video) can come from various free license sites such as Pexels or Pixabay or from a personal archive.

5.2 Database interaction

The backend manages all interactions with the SQLite database, and every major action performed by the user (e.g., registering, logging in, adding pets, sending requests, managing media resources, etc.) is translated into SQL queries, which will be run by PHP.

For example, when a pet is added, the PHP script that handles this adds a new row to the animals table and links the associated media files using foreign keys.

Other actions such as deleting a pet, updating data, managing feeding or medical history, and approving adoption requests also involve SQL operations of the UPDATE or DELETE type. Regarding security, each Backend ensures data integrity and includes protection against SQL injection through prepared statements.

5.3 Media and Data Origins

Media resources (images, videos, audio files) can be optionally uploaded by users while filling out the pet add form. These resources are saved locally in a folder called uploads and are associated in the database via a unique identifier (e.g. the path to the uploads file).

6. Application Features

6.1 Home

Home page contains a news feed section, showing recent adoption activity. An RSS feed is provided for users who wish to see the latest pet listings.

6.2 Register

The registration feature allows new users to create an account by providing a username, email address, and password.

The backend processes the registration request, verifies the format and completeness of the submitted data, checks for duplicate emails, and stores the new user credentials in the database, if validation is successful.

In this case if it is successfull, the user is redirected to the login page. Otherwise, an error message is displayed.

6.3 Add Pets

The Add Pet feature allows logged in users to submit new pets for adoption using a form.

Users can provide details such as the pet's name, breed, pickup address, and optionally upload images, videos, or audio recordings related to the pet.

After submitting the form, the pet is added to the user's personal list and is not visible in the public Browse section.This application enforces predefined values for fields such as region and medical status, to prevent input errors and offer consistency.

The system also allows storing multiple pets at once if they are submitted via a CSV/JSON file.

6.4 My Pets

The My Pets section allows each user to view a list of the pets they have submitted for adoption.

Each pet appears as a card with basic information such as name and species. By clicking on a card, the user is taken to a dedicated management page for that pet.

On the pet management page, an user can:

  • Add or update the pet's description
  • Manage the feeding schedule and a medical history by adding or removing entries
  • Edit other pet-related details such as species, media files, or adoption conditions
  • Permanently delete the pet from the system if needed

This section gives the user full control over the visibility and content of their adoption listings.

6.5 Browse Pets

The Browse Pets section displays a list of all pets available for adoption, excluding those added by the currently logged-in user.

Each pet is presented as a card containing basic information such as name and species. Clicking on a card opens a separate page with detailed information about that pet.

On the pet details page, the user can view relevant details. A dedicated button is available to submit an adoption request for the selected pet.

6.6 Adoption Request

Users can request to adopt a pet by clicking the request button on a pet's detail page.

Once submitted, the request becomes visible to the pet owner, who can choose to accept or decline it. Only one request can be approved per pet.

The requester receives a notification only if their request is explicitly approved or rejected. If the pet is adopted by someone else and their own request remains unanswered, no notification is sent.

Approved requests result in the pet being removed from the system and no longer visible in Browse Pets.
